## 1. 反推 QA.tech：从可观察行为到系统组件

QA.tech 没有公开架构，但四个产品演示暴露了足够多的信息。反推方法：**每个用户可见行为 → 必须存在的组件**。

### 1.1 行为 → 组件反推表

| 可观察行为（动图/页面证据） | 必须存在的组件 | 实现难点 |
|---|---|---|
| 一句话 → 爬 18 页 → 发现登录墙 → 请求凭据 → 继续爬 | Crawler Worker + 认证服务 + 任务中断/恢复机制 | 登录墙检测（表单启发式）+ 爬取任务可暂停 |
| 自动产出 QA 点建议（按业务风险分类） | LLM 提取服务 + QA 点 Schema + 置信度打分 | Schema 约束输出（function calling / JSON mode） |
| 应用地图（页面节点 + 覆盖着色） | **Coverage Graph**（页面/元素/流程图模型） | QA.tech 最有辨识度的资产——图的增量更新 |
| Action Log：时间戳 + 💭 思考 + 子动作 + 截图 | Run 事件流协议 + 执行 Worker + 截图管道 | 事件粒度设计（thinking/action/observation 分离） |
| 三态判定（通过/失败/**无法验证**） | 判定引擎 + "触达验证"检测（覆盖图反查） | UNKNOWN 判定 = 步骤全绿但目标未触达 → 防假绿 |
| 证据面板：截图/视频回放/Network/Console/Trace | 证据管道（Playwright trace/video/HAR 全开）+ MinIO 归档 | 成本：全程录屏 + trace 的存储与索引 |
| PR：Webhook → Preview → **动态生成测试** → SUMMARY/AREAS/TESTS RUN | CI 集成 + Diff→影响分析→测试生成（LLM） | 影响分析的准确率决定 PR 功能价值 |
| Fix in chat → 生成修复 PR | Chat 与产品对象（Artifact）双向绑定 | 对话上下文携带 Run/QA 点对象 |
| 移动测试步骤流与 Web 完全同构 | **Driver 抽象**（Web driver / Mobile driver 换实现不换协议） | 事件模型必须平台无关（我们已预留） |
| 缓存回放 + AI 自愈（Momentic V3 同款） | 元素定位缓存层 + self-heal | 缓存 key 设计（语义 vs CSS selector） |

### 1.2 反推出的核心洞察

1. **QA.tech 的壁垒不在 Agent 本身**——LLM + Playwright 谁都能跑通 demo。壁垒在四件"产品化工程"：
   - **确定性封装**：关键路径确定性步骤，LLM 只做规划与兜底（我们 PRD 的混合执行模型，方向一致）
   - **证据链完整性**：每个判定可下钻到截图/HAR/trace，UNKNOWN 诚实判定
   - **Coverage Graph**：把"测试了什么"变成可计算的图，支撑覆盖缺口与影响分析
   - **Run 事件协议**：一套 step 流协议吃下 Web/移动/PR 三个场景的前端实时渲染
2. **它的 SUMMARY/AREAS/TESTS RUN 三段式** = LLM 对 Run 数据的后处理总结层，不是独立能力——我们的 PR 屏已验证该结构可由 Run 数据生成
3. **Free Plan badge** 说明多租户/配额体系存在，但第一版不需要

## 2. 我们的系统架构（六层）

```
┌─ Web（React 18 + Vite + shadcn/ui + @assistant-ui/react）
│    原型 15 屏 = 1:1 需求稿；WebSocket 实时渲染 Run 流
│
├─ Gateway / API（NestJS 单体）
│    REST + WebSocket(Run 事件流) + 多租户/项目隔离 + 审计
│
├─ Orchestrator（Run 状态机）
│    Run/Step 生命周期 · WAITING_FOR_APPROVAL 门控 · 依赖树调度
│
├─ Agent Runtime（packages/agent-core）
│    Planner(LLM 生成步骤) + Executor(确定性执行 + LLM 兜底)
│    + ToolRegistry(8 内置工具 + MCP adapter)
│
├─ Workers（独立进程，Redis 队列驱动）
│    crawl-worker（Crawlee+Playwright） · run-worker（Stagehand）
│    evidence-worker（截图/trace/HAR → MinIO） · mobile-driver（Phase 5+）
│
└─ 存储
     PostgreSQL(+pgvector)：业务数据 + Coverage Graph + 向量
     Redis：队列 + 元素定位缓存 + 会话状态
     MinIO：截图 / 视频 / trace / HAR
```

**LLM Gateway**（独立薄层）：OpenAI 兼容统一入口，GLM / DeepSeek / Qwen 可配置切换；prompt 模板集中版本化；Langfuse 全量 trace。

## 3. 核心契约：Run 事件协议（先于一切代码）

**前后端、Web/移动/PR 三场景的唯一契约**。先定协议再写代码，这是反推 QA.tech 最重要的工程结论。

```typescript
// packages/shared/src/events.ts（节选）
type RunEvent =
  | { type: 'run.started';    runId: string; target: RunTarget }
  | { type: 'step.started';   stepId: string; index: number; title: string; kind: 'module'|'ai'|'deterministic'|'assertion' }
  | { type: 'step.thinking';  stepId: string; text: string }              // 💭 可多段
  | { type: 'step.action';    stepId: string; action: string; tool: string; args: unknown }
  | { type: 'step.observation'; stepId: string; ok: boolean; detail: string; screenshotId?: string; durationMs: number }
  | { type: 'step.evidence';  stepId: string; kind: 'screenshot'|'network'|'console'|'trace'; uri: string }
  | { type: 'step.completed'; stepId: string; verdict: 'pass'|'fail'|'unknown' }
  | { type: 'run.waiting_approval'; gate: ApprovalGate }                   // 凭据表单/写操作确认
  | { type: 'run.completed';  runId: string; verdict: 'pass'|'fail'|'unknown'; output?: Record<string, unknown> }
```

约定：
- **thinking / action / observation 三分**：前端 Action Log 的 💭 思考、子动作、结果分别渲染（原型已验证该粒度）
- **platform 无关**：mobile driver 产出同一事件流（Launch app 只是一个 step）
- **evidenceId 贯穿**：任何判定必须挂证据，UNKNOWN = 无触达证据

## 3.5 对象模型修正（源自 docs.qa.tech 官方文档反推，详见《qa-tech调研.md》）

调研推翻/细化了若干模型假设，以下为准：

1. **层级**：Org → Project → **Application（Web/Mobile/API 三类型）** → **Environment（含 Preview）**——API Application 用独立 Agent（HTTP + 代码沙箱验证，不开浏览器）
2. **依赖双类型**：`Resume From`（恰好 1 个，浏览器状态+数据，6h 复用窗口，仅同 Environment，Mobile 不支持）+ `Wait For`（多个，顺序+数据，新会话）；Orchestrator 的调度核心就是这两类边构成的 DAG：**链内串行、链间并行（隔离 BrowserContext）、per-environment 并发上限排队**
3. **数据共享**：`Output Values`（Agent 显式保存，跨会话）+ `Clipboard`（同会话自动）
4. **PR 验证 = Preview Environment**：Run API 支持 `applications[].environment.url` override，override 时自动落 `is_preview` 环境记录 + branch/PR metadata——**砍掉独立 PR 流水线设计**，PR 屏（列表/Review 详情/回写）只是这个机制的产品化包装
5. **Multi-Actor**：每用户一条链（各自 root login），链间 Wait For 传值
6. **Test Plan** = per-application 的 environment + device preset 配置集；优先级 项目默认 < Plan < Run API override
7. **资源 ID**：短 ID 语义前缀（`pln_` / `app_` / `run_`）

**里程碑修正**：W2-3 的"探索闭环"扩展为"探索闭环 + **依赖链调度器**（Resume From/Wait For + 6h 复用 + 并发上限）"——依赖链是 Orchestrator 的骨架，必须早于 run-worker 定型。

## 4. 关键决策（8 条）

1. **后端 TS 单语言**（NestJS）：Stagehand / assistant-ui / MCP SDK 全在 TS 生态，Agent 层不跨语言；锐捷 Java 栈用于周边服务（对接网关/禅道的企业集成可另起 Java 侧车）
2. **Plan-Execute 双层 Agent**：Planner 产步骤 DAG（可人工编辑，对应原型步骤列）→ Executor 逐步执行；步骤级"确定性优先，LLM 兜底"——QA.tech 稳定性的来源
3. **Stagehand 定位缓存**：首次 LLM 定位 → 缓存（语义 key）→ 回放零 LLM → miss 才自愈；缓存命中率是成本与稳定性的核心指标
4. **Coverage Graph 用 PG 而非图库**：nodes(page/element/flow) + edges(navigate/act)，JSONB + 递归 CTE 够用；pgvector 存页面语义做相似去重
5. **UNKNOWN 是一等公民**：判定引擎强制"触达校验"——步骤全绿但 Coverage 反查目标未触达 → unknown；这是对 QA.tech 最有价值洞察的复刻，也是我们的差异化信任锚
6. **证据先开全**：run-worker 的 Playwright context 全程 `video + trace + HAR`；MinIO 生命周期 90 天；不做选择性录制（QA.tech 录屏回放是标配体验）
7. **MCP 作为插件协议**：ToolRegistry 统一接口，外部能力（CMDB/禅道/飞书）走 MCP adapter，不发明私有协议
8. **私有化优先**：全组件容器化、无外部 SaaS 依赖、LLM 走客户内网网关或我们代理的国产 API

## 5. 里程碑（10 周 MVP → 内测，2 全栈）

| 周 | 交付 | 验证标准 |
|---|---|---|
| W1 | Monorepo + docker-compose + **事件协议 v1** + LLM 网关 + **P1-P4 PoC**（Stagehand × GLM 实测） | ✅ 已完成：骨架+协议（11/11 自检）+ PoC 4/4 通过（glm-4.5v + 自定义 llmClient） |
| W2-3 | crawl-worker + 凭据动态表单（WAITING_FOR_APPROVAL）+ Coverage Graph v1 + 探索闭环 | 一句话 → 18 页建图 → 3 个 QA 点建议 |
| W4-5 | QA 点提取落库 + 验证编辑器 + run-worker（三态判定 + 证据管道） | 新增员工用例跑通，UNKNOWN 正确判定 |
| W6 | Action Log 实时流（WS）+ 证据面板六 Tab + Triage 归因 | 前端实时渲染与原型一致 |
| W7-8 | GitLab webhook + Diff 影响分析 + 动态测试生成 + SUMMARY/AREAS/TESTS RUN + MR 回写 | 对真实 MR 全自动出 Review |
| W9 | 插件层（db.query 只读 / code.view）+ 概览 Dashboard | db 查询入证据链 |
| W10 | 私有化打包（docker compose 一键部署）+ 权限/审计 + 内测发布 | 客户环境 30 分钟起服 |

**风险与降级预案**：
- ~~Stagehand 对国产模型指令遵循不达标~~ → **A5 PoC 已实测通过（2026-09-04，4/4）**：国产模型组合定论 = **glm-4.5v + @ai-sdk/openai-compatible 自定义 llmClient**（绕过 aiSDK openai 默认 Responses API；GLM 只支持 chat/completions）。降级方案（Playwright MCP + 自研 act 层）保留为二线预案
- GLM 模型选择铁律（实测）：glm-4.6/4.5-air 推理模型对 ~15k+ DOM 注入 prompt 挂起超时（>90s）；glm-4.5 纯文本不收 image_url（stagehand act 必发截图）；**glm-4.5v 是唯一"视觉 + 非推理直出"组合**（大 prompt 14.8s）
- Coverage Graph 过重 → 砍 element 级，先 page/flow 级
- 动态测试生成质量低 → 先"定向回归 + 模板边界生成"，探索生成后置
