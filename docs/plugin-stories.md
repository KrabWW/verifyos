# VerifyOS 插件故事集 —— 每个插件背后都有一个真实踩坑现场

> **为什么用故事记录插件**：插件的价值不等于它的接口列表，而等于「它替人省下的那段血泪」。
> 每个插件的故事 = 一份天然的需求文档 + 一份天然的验收报告。贡献新插件时，请先讲一个真实的故事
>（模板见文末），再谈实现。

---

## 故事一：深夜排障只能 tail server.log → `live-run-events`

**当时在干什么**：分析 ver_5cm3ay 的失败 run_mu54qus9，想知道第 2 步到底发生了什么。

**踩坑**：`GET /api/runs/:id/events` 只在 run **完成后**才有数据（事件落内存 outcomes 是完成时的事）；
运行中查永远是 `{found:false}`。API 一重启，短 id 连历史 run 都查不到。排障唯一手段是 tail server.log，
而插件宿主的 console.log 还不进这个日志。

**人工解法的笨**：盯日志刷屏、等 run 跑完才能看事件流、看门狗重启后线索全断。

**插件怎么自动化**：`live-run-events` 监听 `run.event` 内存缓存（800 条/run、50 run、30min TTL），
执行中 t≈4.5s 即可读：同一时刻核心端点 `found:false`，插件端 `found:true` 已有 2 个事件。
排障从「等跑完翻日志」变成「curl 一下看事件流」。

## 故事二：AI 臆测了不存在的筛选器 → `page-structure`

**当时在干什么**：AI 生成的验证步骤在真实站点 cp-test.ruijie.com 上反复失败。

**踩坑**：步骤写着「时间范围设为很久以前」——页面根本没有时间筛选器；写着「点查询」——按钮实际叫
「搜 索」；登录步骤的 instruction 是「Sign In」「Enter your account」——真实登录页是「统一身份认证平台」
+「立即登录」。LLM 每次靠运气蒙对登录，但臆测的断言必挂。

**人工解法的笨**：开着 devtools 一个个元素看，手抄 selector，抄完页面一改版又作废。

**插件怎么自动化**：`page-structure` 一条 `POST /capture {url, cookie}` 出整页交互 outline
（按钮/input/select 两段式/表头/分页/空态）+ 截图落盘。实测抓 taskList：9 节点里明确
「前往/共 N 条」是纯文本 span 而非控件——这正是当初臆测错的点。生成步骤前先抓 outline，臆测归零。

## 故事三：下拉框点开了却没选 → `locator-composite`

**当时在干什么**：用 AI 步骤测任务列表的「完成情况」筛选（antd Select）。

**踩坑**：run_mu56ypw8 里 act 返回 success——但只点开了下拉没选选项，**假绿**。单步 selector 固化
（LocatorCache）表达不了「点开 → 等浮层 → 点选项」两段式序列。

**人工解法的笨**：逐 run 翻截图肉眼看浮层有没有弹出来。

**插件怎么自动化**：`locator-composite` 采集同一 stepId 的多段动作序列（含 observation 与耗时）
落 `sequences.jsonl`，可查询可统计——为「复合序列固化回放」备料（回放接线是核心缝，文档如实标注）。

## 故事四：六次失败 run 熬出来的 12 步 → `code-forensics`

**当时在干什么**：修复 ver_5cm3ay（8 次失败）。臆测步骤 → 抓页面改 selector → 回归又挂
（假绿 / has-text("搜 索") 空格未命中 / 分页 selector 未命中）→ 再改 → 中间失败 run
run_mu56rtwb、run_mu56ypw8、run_mu573msj、run_mu577a7y、run_mu57d6hh……最后才 12 步全绿。

**人工解法的笨**：失败 → 翻代码仓库找页面片段 → 猜真实 DOM → 改步骤 → 回归。一个循环半天。

**插件怎么自动化**（今天刚实测的自动版）：
- 探针步骤故意用 `input[placeholder*="任务名称"]`（真实页面是「任务标题」，一字之差）→ 一发构造出
  「AI 臆测 UI」失败类（run_mu5e0bj6，62.1s）；
- 失败计数 1→2 越过阈值 → **自动**取证（trigger=auto，autoErrors 为空）；
- 46.7s 出报告：rootCause 指出 `placeholder*=字段名` 与代码库「中文 label + 通用 placeholder」惯例冲突；
  el-pagination layout 无 jumper；分页 `v-if="total > 0"` 空态不渲染的时序坑；6 条带行号引用的
  suggestedSteps；
- 意外收获：报告反向解释了现有 12 步为什么能过——st_a5 重置（恢复数据）在 st_a6 分页跳转之前，
  正好绕开了空态分页不渲染。谁要是把这两步换序就会挂，而坑已经写在报告里了。

半天的活变成 46.7 秒。

## 故事五（番外）：证据明明录了却看不见

不插件、纯核心 bug，但故事模式同样适用：执行成功后页面「证据」链接 404、截图 tab 空白——
排查发现采集一直在正常落盘（16 个文件：截图/webm/trace/HAR），断的是**展示层**
（Express5 无通配路由 + 短 id 查不到历史 run）。教训：「没有」先查「是不是没显示」，再查「是不是没采集」。

## 给贡献者的故事模板（PR 必附）

```markdown
### 故事：《一句话标题》
1. **背景**：我当时在做什么任务（一句话，带验证/页面名）。
2. **踩坑**：具体现象 + 硬证据（run id / 报错串原文 / 截图路径）。
3. **人工怎么解决的**：走了哪些弯路，诚实记录（弯路就是插件的价值证明）。
4. **插件怎么把这个人工活自动化**：机制一句话 + 关键接口。
5. **验证**：数字收尾（事件数 / 耗时 / 命中文件数 / 报告结构完整性）。
```

**三条纪律**：①用真实 run id 和原始报错串，不用「有时会失败」；②保留弯路——顺的过程没有故事；
③必须以可复验的数字收尾。
